- Real provider data is read-only: pure mappers here turn provider responses into monthly values stored only as imported results through the server-attested import function; currencies stay separate. Writes exist only for simulated providers (`sim.` keys), whose records live in the sandbox table, so no customer system can change in this phase.
- Credentials enter only through server functions, go straight to server-attested Vault storage and are never returned to the browser; providers accept only read-only credential types, so a leaked key cannot change customer systems.
- Google sign-in returns only to origins in the server's `APP_PUBLIC_ORIGINS`, uses PKCE with an HttpOnly verifier cookie and constant-time state checks, because a browser-supplied origin could otherwise receive the authorization code.
- External actions follow one database-owned lifecycle (proposal 0065): connections grant six separate permission levels, only draft level in bounded autonomy is policy-approved, execution and verification are server-attested, and an uncertain outcome is resolved only by a provider lookup, so nothing runs twice or skips approval.
- `catalog.ts` mirrors the SQL provider, action and specialist rules and a test compares them, so screens never offer what the database refuses.
