# Shared logic
- Evidence freshness is pure `src/lib/evidence-freshness.ts` by source kind: historical records never expire, expired/deleted/unconfirmed sources count only as estimates, and absence is "missing" only when the read was complete, so nothing stale is presented as proof.
- Fact conflicts (proposal 0074) are detected by pure `src/lib/fact-conflicts.ts` using the same topic rule as SQL `fact_topic`, are never auto-resolved, and are decided by an editor through `resolve_fact_conflict`, which keeps every value and audits the choice.
- Conflict lifecycle and recommendation postpone/dismiss/restore (proposal 0075) are insert-only event rows; status is derived by pure `conflictStatus` / `recommendation-memory.ts`, and a dismissal is keyed to a fingerprint so a recommendation returns only when its information changes.
- Growth levers are checked by pure `src/lib/growth-levers.ts` from the business's own records; it reports available and missing data per lever and never implies a result.
- Business facts used for conflicts and source checks are read completely in ID keyset pages (`src/lib/facts-read.ts`, hard ceiling); an incomplete read is reported, never treated as "no conflicts" or "missing source".
- Business checks (proposal 0076) are insert-only snapshots of deterministic signals started by a member; the database computes the change summary, and a frequency only marks a check as due, so no background monitoring is claimed.
- Campaign progress (`src/lib/campaign-health.ts`) uses the campaign, its tasks and, when completely read, its spend ledger summary; without the ledger it never claims a budget overrun.
- Task re-planning (proposals 0077–0078) is computed by pure `src/lib/task-replan.ts` at no credit cost and stored as insert-only proposals and decisions; only editors apply an option, atomically and refused when the task changed since the proposal, so stale plans never overwrite newer ones.
- Campaign spend is an insert-only per-campaign ledger (spend, reservation, release, correction) with request-key and reference de-duplication; `spendSummary` in `campaign-spend.ts` is the only classification of campaign money: actual and simulated totals are kept apart, budget warnings come from actual entries only and simulated overruns are separate labelled warnings, so no screen, report, signal or AI context can read test data as a real overrun.
- Business reports are pure `src/lib/reports.ts` over caller-RLS reads: every figure is recorded or computed from recorded rows for a period and the previous period of equal length, estimates are kept apart and missing inputs are listed instead of shown as zero.
- Command Center tiles come from pure `src/lib/business-tiles.ts` over caller-RLS reads; each carries kind, source and period or is withheld with a reason; revenue only from imported sources, so no figure is invented.
- Costs: pure `src/lib/cost-rollup.ts` over RLS reads: each task once per level, budgets per currency, no unattributed revenue/ROI.
- Evidence (proposal 0073) is typed, record-checked and insert-only; labels from pure `src/lib/evidence.ts`; AI text is never independent evidence.
- Specialist quality control (proposal 0081): a second review is one metered call by a different task specialist; the database recomputes score/verdict and requires a review before an editor accepts important results; reviews are advice, never evidence.
- AI re-planning analysis (proposal 0082) explains a rule-built proposal in one metered call bound to that proposal; it may recommend only the proposal's own options, is insert-only, goes stale when the task changes, and never applies anything.
- Campaign diagnosis is pure `src/lib/campaign-intel.ts` over the spend ledger, campaign-linked metrics and linear attribution; ratios exist only when both inputs are recorded, problems follow named thresholds, and advice only creates internal tasks.
- Growth Situation Analysis is pure `src/lib/situation.ts` over caller-RLS reads: a section without data is "unknown", never "good"; conflicts come from the insert-only conflict history (undetermined when facts or history are incomplete); each section has a reason, confidence and next step; the AI explanation (`situation-narrative.ts`) may only cite those findings, and statements resting only on simulated/estimated findings cannot be facts.
- Budget allocation (proposal 0084): a budget line is shared by campaigns only through insert-only allocation events applied under row locks by role-checked RPCs; spend may name its line and is refused above the campaign's allocation, so money is never assigned twice. Pure views in `budget-allocation.ts`.
- KPI comparisons (`kpi-periods.ts`) use corrected actual results over non-overlapping periods of equal length only; confidence rises above "low" only when a change exceeds the metric's earlier fluctuation, and nothing claims a cause.
- Campaign AI cost (`campaign-ai-cost.ts`, `econ/ai-cost.ts`) counts recorded run, retry and review credits only, keeps uncertain/uncharged runs apart, and values each credit at the price version in effect when it was used; credits without one stay credits.
- Growth economics (proposal 0085) is pure `src/lib/econ/` over caller-RLS reads: every amount has one home (campaign spend ledger, business cost ledger or AI credits), parents add their own costs and each linked campaign once, currencies and actual/estimated/simulated/reserved stay apart, credits become money only through the price version valid at use, and profit/CAC/customer value report missing inputs instead of numbers.
- Growth economics figures on the page, Growth Officer context, Home alerts, reports and the organization view come only from `econ/read.ts` + `econ/summary.ts`, so every screen shows the same numbers; refunds count in the period of their sale everywhere, and AI totals come from the usage ledger.
- Credit price history (proposal 0086) is readable and writable only by the Platform Owner through server functions and `set_credit_price`; other users see only prices in effect via `credit_prices_in_effect`, and credits used without a price stay credits.
